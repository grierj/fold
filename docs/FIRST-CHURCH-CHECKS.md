# Checks to run by hand when the first church starts using Fold

An agent can't run these: they need real phones, real mail providers, a real domain or a real server. Each was built best effort and merged without them (DEC-128). Run them once, when the first church starts using Fold, and fix what you find. When a PR adds a check like this, it adds a section or an item here in the same PR.

Each item says what to do, what you should see, and the milestone it came from.

## Web push (M3.13)

Follow the directions page at `/notifications/setup` literally, on each device below. Record the iOS version you used.

- [ ] **iPhone or iPad, iOS 16.4 or newer, Home Screen app.** Add Fold to the Home Screen, open it, sign in, go to Me → Notifications and tap "Turn on notifications". You should see the iOS permission prompt only after the tap. Tap "Send a test notification", lock the phone, and see it on the Lock Screen. Then set Settings → Notifications → Show Previews to "When Unlocked": you should see the text hidden on the Lock Screen and shown after unlocking, as the directions page says.
- [ ] **Android, Chrome.** Same steps, with or without the app installed. You should see the Chrome prompt and the test notification.
- [ ] **Desktop Safari (Mac).** Same steps. You should see the Safari prompt and a macOS notification.
- [ ] **Edge on Windows.** Same steps. You should see the test notification. This also confirms the Windows push host (`notify.windows.com`) is on the allow-list.
- [ ] **The Apple and Microsoft push hosts** stay marked unsure in `docs/plan/research/web-push.md` until the checks above show each one working. Add any host that fails to the allow-list, and say so in the PR. Samsung Internet uses FCM endpoints, so it needs no host of its own.
- [ ] **`fold push check` on the server** (`smoke.sh` runs it and only warns). You should see OK for every push host. The bare name `notify.windows.com` doesn't resolve, so the check probes `wns2-bl2p.notify.windows.com` for Edge; if Edge's real endpoints use a host that fails, set it in `probeHosts` (`internal/push/allow.go`) (M3.13a).
- [ ] **Revoking.** Turn notifications off for the site in the device's own settings, then trigger a send. You should see the next send record `device gone` and the device disappear from Me → Notifications. Then use "Turn off notifications on this device" on another device and confirm the row goes.
- [ ] **Logout.** Sign out on a shared device. You should see no notification meant for the first person arrive afterwards.
- [ ] **The Home Screen app's name and icon (M3.13c1).** On the iPhone and on Android, after adding Fold to the Home Screen, you should see the church's name under the icon (or "Fold" when the name is longer than 12 characters). The page has no `apple-mobile-web-app-title` tag, so iOS has to take the name from `/manifest.webmanifest`. The icon should be the violet Fold mark, with no black corners on iOS and nothing cut off in Android's round mask.
- [ ] **The signed-out Home Screen app (M3.13c1).** Open the Home Screen app before signing in to it, even if Safari is signed in. You should land on Log in with "Sign in once here and your notifications will come to this app." above the form.
- [ ] **Tapping a notification (M3.13c1).** With Fold open, tap a notification: you should see that window come forward on the notification's page. With no Fold window open, you should see one open on that page. Try once with a tab opened before you turned notifications on: the worker claims open tabs when it starts, so you should see that tab come forward on the right page too.
- [ ] **The icon's count (M3.13c1).** On the Home Screen app (iPhone, Android) and an installed desktop app, you should see the bell's count on the icon, and see it clear after you mark everything read.
- [ ] **On again after a password change (M3.13c1).** Change your password from a computer, then sign in again on the phone and open Me → Notifications. You should see "Notifications are on for this device" without tapping anything: the card saves the phone's subscription again, once.
- [ ] **The blocked steps (M3.13c1).** Block notifications on each device above, then open Me → Notifications. You should see "This device is blocking notifications from <church name>" with that platform's steps, and following them should bring back "Turn on notifications". Note any menu path that differs.
- [ ] **An iPhone on iOS older than 16.4**, if one is around (M3.13c1). You should see "Notifications on an iPhone or iPad need iOS 16.4 or newer" and no Home Screen steps.
- [ ] **An announcement's push (M3.13d2).** With notifications on for an iPhone (Home Screen app) and an Android phone, have a leader send their group an announcement between 8 AM and 8 PM, with "Push notification too" on. You should see one email and one notification on each phone: the subject as the title, the first line or so of the message, then "Open to read.", with no link in it. Tap it: you should see the message open in Fold, read only, "From <leader> via <church>". On the message's page the leader should see "Push notifications: N pushed", one per person whatever their device count. Send one after 8 PM: you should see the email at once and the notification at 8 AM, and the page say "1 waiting until 8:00 AM" until then. Turn off "Messages from leaders" email (not Push) on one phone's account and send again: that phone should get the notification and no email, and its tap should still open the message.
- [ ] **The 2-hour push reminder (M3.13d3).** With notifications on for an iPhone (Home Screen app) and an Android phone, RSVP Going to a 7:00 PM date from each and leave the server running. At about 5:00 PM you should see one notification on each phone, "Reminder: <event>" and "Starts at 7:00 PM", with no place, no link and no bell row in Alerts; tap it and you should see that date's page with the place. Make a 9:00 AM date the next morning and RSVP Going: you should see its notification at 7:59 PM the evening before ("Starts tomorrow at 9:00 AM"), not at 7:00 AM. As the event's leader, open each date's page: you should see "Reminder pushed to N people" with the time, opening its history. Then uncheck "Push reminder 2 hours before" in Edit series on a third date before its time, and cancel a fourth: neither phone should get anything for them.

## Live install (M5.1, M5.3)

The recovery tooling (R4-RP, `restore.sh` and its interim operator notes in
`docs/DEPLOY-DIGITALOCEAN.md`, "Restoring a nightly dump") is on master and has
been drilled only on disposable Compose stacks with fixture recovery levels. That
does not verify the restore procedure and does not authorize a release. Every
restore item below is unchecked, and a release at `recoveryPolicy` 1 or higher
(this tree reports 2) stays unpublishable until they are done (#310). Inventory
section 11 cross-references these items.

- [ ] **`docker compose up` on a real domain.** Fill `.env` (set `FOLD_VERSION` to the published release), run `docker compose pull && docker compose up -d`. You should see Caddy get a certificate, `https://<domain>/healthz` answer, and the setup wizard at `/setup`.
- [ ] **Pull-only install on a machine with no Go and no Node (R1 slice 1, C10).** After the first release is tagged and the `release` workflow is green, make the `ghcr.io/grierj/fold` package public (or `docker login ghcr.io` with a read token), then on a fresh server with only Docker run `docker compose pull && docker compose up -d` with `FOLD_VERSION` set to that exact version. You should see the image pull with no build step (try an `arm64` machine too, if one is around) and the setup page at `/setup`. Also run `gh attestation verify oci://ghcr.io/grierj/fold@<digest> --repo grierj/fold` with the digest from the workflow summary: you should see it verified.
- [ ] **A 1 GB droplet with swap stays up on the pulled image (R1 slice 1).** Provision an `s-1vcpu-1gb` droplet with `--image ghcr.io/grierj/fold:<version> --swap-mb 1024`. You should see `smoke.sh` pass, the wizard reached, and the app and Postgres still up (`docker compose ps`, `free -m`) after a day of normal use and a week of reminders and push.
- [ ] **Large pictures on a 1 GB droplet with swap (#356).** On the droplet above, with throwaway accounts, upload the largest pictures Fold accepts, several at once from different browsers: a 25-megapixel PNG, a 12-megapixel JPEG that needs turning, and a long animated GIF, each as a profile photo and as a group cover. Some may answer "Other pictures are being uploaded right now"; the rest should save. Watch `free -m` and `docker compose ps`: the app and Postgres should stay up with no restart, and uploads should work again at once afterwards. The estimate behind the limit is from the Go decoders, not measured on this machine.
- [ ] **Volumes survive an upgrade.** Upload an avatar, then run the installed `/opt/fold/upgrade.sh --image ghcr.io/grierj/fold:x.y.z --source-dir /root/fold` with the next release. You should see the avatar and all data still there (`pgdata`, `uploads`).
- [ ] **Recovery refusal and failure guidance (M7.4 R4-RP-V).** On a disposable copy of the droplet, use the installed `upgrade.sh` to start a higher-level image and deliberately fail smoke. Confirm the message says a lower-level rollback is refused and directs you to recovery with the current release. Confirm `--rollback` refuses before stopping the app or restoring data. Keep the pin and floor intact, and follow the restore notes in `docs/DEPLOY-DIGITALOCEAN.md`, using `restore.sh --dump` with the current release. Do not attempt this failure on the live church database.
- [ ] **Refused rollback and refused forward upgrade, read on the droplet (R4-6c-V).** On a disposable copy at the current recovery level (2 today; level 1 or higher), run the installed `upgrade.sh --rollback` toward a level-0 release, then `upgrade.sh --image` and `--commit` toward a level-0 target. Each must exit non-zero before a backup, checkout or pin changes, and the message must name the restore barrier and point to restoring with the current release. Read the wording; it is what an operator sees under stress.
- [ ] **Release order for the restore barrier.** Before publishing any release that reports recovery policy level 1 or higher, land and verify R4-6c-R's current-release restore tooling and its operator procedure. Until then, no such release is publishable: a failed upgrade can refuse the older rollback, and the scripted restore is written but not yet verified on a real droplet or at an exact landing head.
- [ ] **`restore.sh` on the real droplet, with sign-in through the SSH tunnel (R4-6c-V).** On a disposable copy of the droplet at the current recovery level (2 today), with throwaway accounts: take a `backup.sh` dump, delete a throwaway account, then run `sudo /opt/fold/restore.sh --dump <dump> [--image ...]`. You should see the public site refuse connections, a count of 1, and `backup.sh` exit 75 meanwhile. Open `ssh -N -L 18080:127.0.0.1:18080 <admin>@<droplet>` and `http://localhost:18080` in Chrome and in Firefox (Safari is not recommended; note what it does), sign in as admin, and delete the account again. Run `restore.sh --reopen --checked-church-records`: you should see `smoke.sh` pass, the old database gone, the lock removed and the church reachable over HTTPS. Then run `backup.sh` by hand, and confirm the next day's legacy sweep runs without error. Record any browser that loses the session.
- [ ] **A reason-review panel across a `restore.sh --dump` restore (T07B-2-V).** This is the check of the React panel; the restore drill only checks the server protocol with curl. On a disposable copy of the droplet at recovery level 2, with three throwaway accounts X, Y and Z, each holding two contact-request reasons (one as requester, one as subject; give Y one of them as a pending request whose requester you can sign in as). Sign in as admin in Chrome and take a `backup.sh` dump. Open the Delete panel of X and of Y, load their reasons and choose Keep for one reason and Blank for the other in each, but never press Delete on either: an open panel holds no attempt id, each press mints one. For Z, open the panel and choose the same way, then in DevTools, Network, Network request blocking, add two patterns: `*/api/v1/admin/users/<Z's id>` (only the DELETE has exactly that URL; the review pages and the other panel requests have longer ones) and `*/operation-attempts/settle`. Press Delete once. The mint (`POST .../operation-attempts`) is not blocked and succeeds, the DELETE never reaches the server, and the panel stays on "checking" and then "Still checking" with Delete off. Do not use DevTools' offline switch for this: offline blocks the mint too, no attempt then exists and the panel only shows an error. Leave the tab open. Run `sudo /opt/fold/restore.sh --dump <dump>` with the current release, then `restore.sh --reopen --checked-church-records`. Remove only the settle pattern and press Check again: the app restarted, so the old attempt id is unknown, and the panel says "Fold can't tell whether an earlier delete finished. Reload this person's page to check." with Delete still off. Click Close. The users list reloads and Z is still listed (if the list fails to load, Delete stays off when you reopen Z's panel). Remove the DELETE pattern, open Z's Delete panel again: the reasons load afresh and your earlier choices are gone, so choose again, press Delete and confirm Z is deleted with exactly your choices. Now X: press Delete on the panel you left open; it deletes at once and applies exactly the two choices (the kept reason keeps its text, the other is empty), with nothing about an expired attempt. Y: before pressing, sign in as the requester in a private window and withdraw the pending request, then press Delete in Y's panel. It says the reasons changed, reloads with that item marked, nothing is blanked, and after you choose again the press applies your choices. In no case should a choice land on a different reason. Also read the refusal from a level-2 host toward the level-1 release: `upgrade.sh --rollback`, `--image` and `--commit` must exit non-zero before anything changes, and the message must name reason review.
- [ ] **A droplet reboot during recovery (R4-6c-V).** In private recovery, reboot the droplet. After it comes back, `docker compose ps -a` in `/opt/fold` should show the app, Caddy and the recovery container all stopped (no public answer on 80 or 443). `restore.sh --resume` should replace the recovery container with no name conflict and end in private recovery again.
- [ ] **A reboot after an interrupted reopen (R4-6c-V).** Interrupt `--reopen` (for example kill the shell after the app and Caddy start), reboot, and note whether the app and Caddy come back running. `restore.sh --resume` must stop them (Caddy, then the app) before it restarts private recovery, and the public site must not answer in between once `--resume` has run.
- [ ] **Backup expiry on the real droplet (R4-6c-V).** With `FOLD_BACKUP_KEEP_DAYS` short on a disposable copy, confirm old dumps expire after the first `backup.sh` run that follows a finished recovery, and that no dump, expiry or offsite upload happens while `recovery.lock` exists.
- [ ] **The delete dialog on a phone (R4-6c).** Open Admin → Users → Delete on a real phone (iPhone Safari and an Android browser). The backup and outside-copy wording should read plainly, nothing should clip at the phone's width, and the buttons should be reachable.
- [ ] **A real restore is noticed (M7.4 T07B-1; these hand steps deliberately bypass `restore.sh` to exercise the barrier, and are not the recommended restore, which is in `docs/DEPLOY-DIGITALOCEAN.md`).** Only on a disposable copy of the droplet, never the live church database, and only for a release that reports recovery level 1. Make four throwaway member accounts X, Y, Z and W with no events or groups, and sign in as an admin. (1) Delete X in Admin → Users. (2) Dump the database: `docker compose exec -T db pg_dump -U church -Fc fold > /root/before.dump`. (3) Delete Y. (4) Restore the dump into the running database: `docker compose exec -T db pg_restore -U church -d fold --clean --if-exists --no-owner < /root/before.dump`. If `pg_restore` waits on the app's open connections, note that in your report and do not stop the app, since the check needs it running. (5) Reload Admin → Users: you should see Y again, because the restore lost its deletion. (6) Press Delete on Z and confirm: you should see "Fold noticed its database was restored while it was running, so nothing was changed. It is restarting; try again in a minute." and Delete stay off for every person until you reload the users list. (7) After the app is back, delete Y and Z with new presses: each should end "The account was deleted."
- [ ] **The restore restart works under Compose (M7.4 T07B-1).** During the check above, watch `docker compose ps` and `docker compose logs app`. You should see one log line "Stopping: the database was restored while Fold was running", the app container restart by itself (`restart: unless-stopped`) with a small restart count and a fresh uptime, `/healthz` answer again within a minute, and no further restarts in the next ten minutes. A container that keeps restarting, or one that stays down, fails this check.
- [ ] **A pre-restore delete attempt never claims nothing was deleted (M7.4 T07B-1).** Repeat the restore check with W, using any HTTP client signed in as the admin (copy the session cookie and the `X-CSRF-Token` header value from your browser's developer tools). After step (2), `POST /api/v1/admin/operation-attempts` with `{"kind":"account_delete","subjectUserId":<W>}`, then `DELETE /api/v1/admin/users/<W>` with `{"attemptId":"<that id>"}`; you should get 200. Restore as in step (4), and let the app restart (a request sent before the restart may answer `restore_detected`; send it again after). Then `POST /api/v1/admin/operation-attempts/settle` with the same id, kind and subject: you should get `{"result":"history_unavailable"}`, never `not_applied`. `DELETE` the same id again: you should get 409 with code `attempt_expired`, and W still exists. In the panel, the same situation should read "Fold can't tell whether an earlier delete finished. Reload this person's page to check." and never "Nothing was deleted by this attempt."
- [ ] **Reviewing reasons over plain http, where the browser has no crypto.subtle (M7.4 T07B-2).** On a real phone or laptop, open Fold over `http://<LAN address>` (not localhost, which counts as secure) with a throwaway account that has two or three contact-request reasons. Admin → Users → Delete: choose Keep or Blank for each reason and press Delete. You should see "Preparing your choices…" for a moment and then "The account was deleted." with the right counts: Fold's own SHA-256 does the work when the browser offers none. Then repeat on `https`: the result should be the same. If the first run shows "This browser can't prepare the review safely", note the browser and version.
- [ ] **Reviewing many reasons on a real phone (M7.4 T07B-2).** With a throwaway account that holds at least 120 reasons (one leader asking again and again is enough), open the Delete panel on an iPhone and an Android phone. You should see "Reasons 1 to 50 of …" with Previous 50, Next 50, a "Go to reason number" box and "Next reason without a choice", no sideways scrolling, and a tap on Keep text or Blank text answering at once. Choose every reason by hand and delete: the account should be deleted and the counts match.
- [ ] **A lost answer on a real connection (M7.4 T07B-1, best effort).** With a throwaway account, press Delete in the panel and, as it is sent, turn the device's network off (airplane mode, or the browser's offline switch). You should see "Still checking" and no "nothing was deleted" wording. Turn the network back on and press Check again: you should see either "The account was deleted." or "Nothing was deleted by this attempt.", and the account list should agree. The timing is hard to hit, so if the answer arrives first, repeat with another throwaway account and say how many tries it took.
- [ ] **Only one installed maintenance operation (M7.4 R4-RP-V).** During an upgrade on the real droplet, run a second installed `upgrade.sh`. It must exit 75 and identify the first operation. Never delete `ops.lock`. If the named pid has exited but exit 75 persists, inspect `sudo fuser -v /opt/fold/ops.lock` and stop only a verified abandoned operation or helper before retrying.
- [ ] **Profile photos are cleaned up on the real volume (M7.4 R4-5).** With a throwaway test account (not a real member's), upload a profile photo, replace it, remove it, upload again, then delete that account as an admin. After each change you should see `/data/uploads/avatars/<id>/` hold only the current file (look inside the container or on the `uploads` volume), and after the deletion the folder should disappear within a minute. Admin, System should show no dead `Removing old profile photos` or `Finding leftover profile photos` task.
- [ ] **`deploy/digitalocean/provision.sh` as a real run**, not `--dry-run`, on a fresh droplet the church owns, then `smoke.sh`. You should see health, TLS, and that Postgres and the app are not published. After the first dump, run the backup restore test (`--restore-test`) from `docs/DEPLOY-DIGITALOCEAN.md`.
- [ ] **Following the deployment docs** on a fresh 2 GB VPS reaches the wizard in under 30 minutes (M5.4).

## Email (M3.2, M3.3, M3.4b, M3.5, M3.6)

- [ ] **A real reminder, on time.** Make an event a day and a bit out with "1 day before", RSVP Going from one account and join the waitlist from another (with a capacity of 1), and leave the server running. You should see the reminder arrive within a few minutes of 24 hours before, with the time in the church's zone, and the waitlist note to the other account; restart the server near the reminder time and you should still get exactly one. Afterwards, as the event's leader, open that date's page: you should see "Reminder emailed to 1 person" and "Waitlist note emailed to 1 person" with the time they went, each opening its history (M3.6).
- [ ] **Postmark, a real send** on both the transactional and the broadcast stream. You should see each arrive, and Postmark's activity page show the right stream (M3.2).
- [ ] **Postmark webhooks.** Cause a delivery, a bounce and a spam complaint. You should see each reach `/hooks/postmark/email` with its Basic credentials and update the person's suppression, and the new `suppressions` row has a 64-character `address_hash` (M3.2, R4-S).
- [ ] **The database encoding.** On the church's own server run `docker compose exec db psql -U church -d fold -c 'SHOW server_encoding'`. You should see `UTF8`. Suppression matching assumes a UTF8 database with a deterministic default collation, which the shipped Postgres image gives (R4-S).
- [ ] **One-click unsubscribe over https.** In Gmail and in Apple Mail, use the client's own unsubscribe button on a Fold announcement. You should see the person's "Messages from leaders" switch turn off, with no sign-in (M3.3).
- [ ] **Address-bound optional email links (M7.4 R4-2d2).** On a real HTTPS domain, repeat the one-click check above in Gmail, Outlook and Apple Mail using a version 2 optional email. Open `/email-settings` without signing in and confirm the category switch is off. In each client, open the longer settings link even when it wraps across lines and confirm the page opens.
- [ ] **HTML email rendering.** Send a composed announcement with a button, a link and an image to Gmail (web, iOS and Android), Apple Mail, and Outlook desktop, in light and dark mode. You should see readable text, working links, and the church name and address in the footer. The button's padding is a known gap in Outlook desktop (M3.4b).
- [ ] **The church's SPF, DKIM and DMARC** pass for the sending domain (check a received message's headers; the wizard step is M4.4).
- [ ] **An announcement through Postmark.** Set "Where replies go" to the church office, schedule a message to a small group, and wait for it. You should see it arrive From "<your name> via <church>" in Gmail and Apple Mail (not flagged as spoofed), Reply go to the office address, the message show Sent, and a delivery report move each person to Delivered (M3.5).
- [ ] **A Postmark outage.** Point Postmark's token at a wrong value for an hour, then schedule a message. You should see the message end as Failed, with Postmark's error for an admin and plain words for its leader, and "Try again" send it once the token is right. Postmark's activity page should show one email per person, with nobody it had already reached getting a second (M3.5, DEC-131).
- [ ] **A big send's history.** Send to everyone at church (or a group of 200 or more). You should see the page count up ("Sending… 40 of 230 so far") and settle as Sent without a reload, "See who got it" list 200 names and "And 30 more", and, after Postmark's delivery reports arrive, people move from Sent to Delivered (M3.5b).
- [ ] **A guardian copy in a real inbox.** Turn on Admin → Settings → "Send guardians a copy of messages to their teens", then send to a group with a teen whose guardian is confirmed. You should see the guardian get "Copy: <subject>" with the line "Copy: sent to <teen> because your church sends guardian copies", the teen get the message as usual, and the history show an admin the guardian with "Copy for <teen>" while the leader sees only "1 guardian copy sent" (M3.5b, DEC-19, DEC-132).

- [ ] **A real mail provider outage (M7.5, R6-3).** Set the mail provider's credentials to a wrong value, then cause a notice that emails (for example, approve a group). You should see the notice retry, then go dead after its last attempt, with the email left Deferred and one bell alert per admin titled "A background task stopped: …" with no address, key or error text in it. Put the right credentials back, open Admin → System, and press Retry on that task: you should see the email sent once, the alert close for every admin, and the task leave the list. Dismissing it instead should close the alerts as dismissed and send nothing. The alert is written after the task dies and is not atomic with it, so if the server was stopped at that instant the task is still on Admin → System without a bell alert.

- [ ] **A direct account email after recovery (M7.5, R6-4).** With a test account and the real provider, briefly make the provider unreachable, request a password reset, and restart Fold after the request finishes. Restore the connection before retries run out. You should receive a working reset link after recovery, without requesting another. If the provider accepted an earlier attempt before the connection failed, more than one email may arrive; use the latest link, and confirm earlier links no longer work. Then try an invitation and an email change: delayed mail must not gain a later expiry, and cancelling the email change must prevent its queued verification from changing the address.
