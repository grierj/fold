# M1.5 bot brief. Capacity, waitlist, pruning

This brief turns milestone M1.5 into work one bot can do without guessing.
It is for the bot that claims M1.5 and for the person who reviews its pull request.
For a church member, a full event stops taking sign-ups, holds a fair line, and tells the next person when a seat opens.
For the next engineer, all seat counting sits in one locked transaction and one pure promotion function.

Read these files first and in this order.

1. `docs/plan/PLAN.md` milestone M1.5, section 5.4, section 5.12, and decisions DEC-20, DEC-30, DEC-38, and DEC-47.
2. `AGENTS.md` in full. It owns test layout, migrations, policy, audit, notifications, and form rules.
3. `STATUS.md`. Claim M1.5 there before you write code.

Precedence is fixed. Section 15 decisions in the plan win over `AGENTS.md`. `AGENTS.md` wins over this brief on repo mechanics. This brief wins over habit from other repos.

## Goal

Give one occurrence of one event an optional seat capacity.
A sign-up that fits is `going` at once.
A sign-up that does not fit is `waitlisted` when the waitlist is on and refused when it is off.
A freed seat promotes the earliest waitlisted party that fits.
A leader or host can remove any registrant and can promote or add by hand.
People hear about cancellations, time or place changes, removals, and promotion in the bell and by email.

## Success criteria

- [ ] 50 concurrent "going" requests on a 10 seat event give exactly 10 going and 40 waitlisted in a Postgres test.
- [ ] Cancelling promotes the earliest entry that fits and skips a party too big for the free seats.
- [ ] No auto-promotion runs inside 2 hours of the start. The leaders or hosts get a notice instead and can promote by hand.
- [ ] A promoted person gets an email with a one-click "I can't come" link. The link frees the seat again.
- [ ] There is no approval step. A sign-up is `going` or `waitlisted` at once. A leader or host can remove anyone and the removed person is told.
- [ ] A disabled account stays off attendee lists and out of capacity, waitlist, and attendee counts.
- [ ] Re-enabling an account that would overfill an occurrence drops the registration, writes an audit row, and tells the person to ask a leader or host. A leader, host, or admin can add them back over capacity by explicit choice.
- [ ] Cancelling an occurrence or changing its time or place gives each going or waitlisted person one bell item and one email. A cancellation item is never batched. A promotion gives "you're in".
- [ ] After an occurrence ends, its event items show under Archived and are not deleted.
- [ ] A waitlisted person sees their own position. The text reads "You are #3 on the waitlist".

## Scope

- Guest registration through the same seat rules after email verification.

- The DEC-38 and DEC-47 rules for disabled and re-enabled accounts on registrations.

- The jobs table, the 15 minute email delay, and reminders. M3.1 and section 7.7 own them. Reminders never enter the bell.

## Design

Name the data shape first. Model the Domain shaped this section. One status field holds the registration lifecycle. No boolean pairs stand in for it.

### Data shape

Add one new goose migration. Its number is the next free number on fresh `master`. It is `00015` if M1.4 merged last. Never edit an old migration. Update the GORM models in the same pull request. No new table means no new entry in `models.All()`.

`events` gains three columns.

- `capacity` is a nullable positive integer. Null means unlimited.
- `waitlist_enabled` is a boolean with default false. It matters only when capacity is set.
- `guests_allowed` is an integer from 0 to 5 with default 0. It caps extra unnamed guests on one registration.

`event_occurrences` gains one column.

- `capacity_override` is a nullable positive integer. Null means the occurrence uses the event capacity.

`registrations` gains five columns and two statuses.

- `guest_count` is an integer of 0 or more with default 0.
- `waitlisted_at` is a nullable timestamp. It states when the current wait began.
- `promoted_at` is a nullable timestamp.
- `removed_by` is a nullable user id with no foreign key association in GORM.
- `removal_note` is text with default empty.
- Status gains `waitlisted` and `removed`. Update the database CHECK and the Go constants `RegWaitlisted` and `RegRemoved` together.

Keep `AttendanceMode` and every remote column out of this migration. Decision 1 owns that line.
Keep `household_person_id` out. `user_id` stays required in this milestone.

### Seat rules

The effective capacity of an occurrence is its override when set and the event capacity otherwise.
One `going` registration uses `1 + guest_count` seats.
`maybe`, `declined`, `cancelled`, and `removed` use no seats.
A disabled or deleted account uses no seats. Reuse the `listedUsers` join semantics for every count.
A guest account with status `guest` uses seats like any other listed account.

Put the pure rules in the `internal/events` package in a new `capacity.go` file.
The package already owns occurrence and series logic.
Give it one function that picks promotions from facts. It takes the effective capacity, seats already used, and the waitlist in order with one seat size per entry. It returns the entries that fit in order and skips an entry that does not fit. Give it one helper for seats used and one for the effective capacity.
Add pure policy helpers only where a permission is new. Pruning and manual promotion use `policy.CanManageEvent`. No new permission function is needed unless a test shows one is missing.
Handlers load facts and call these functions. Handlers never recount seats with ad hoc queries in more than one place. One counted query shape serves the lock path and the read path.

### The one locked write path

Every write that can change seats runs in one transaction. The transaction locks the occurrence row first with `SELECT ... FOR UPDATE`. It then recounts seats inside the lock, writes, runs promotion when a seat freed or capacity grew, writes audit and notification rows, and commits. Email delivery runs after commit through the existing `deliverNotificationEmails` pattern.

Route these writes through that path.

- `PUT /api/v1/events/:id/registrations` for a member. The body gains `guestCount`.
- Guest confirmation redeem in `api_guest.go` and guest cancel by manage token.
- Removing a registration, promoting by hand, and adding over capacity. All three are new leader and host actions below.
- Disabling a user who is `going` on future occurrences. Each freed seat can promote.
- Raising the event capacity or an occurrence override. Promote on every future scheduled occurrence whose effective capacity grew.
- Re-enabling a user. The restore check below runs per occurrence under the same lock.
- Lowering capacity removes nobody. It writes the new value and blocks new `going` results until use drops below it. This matches the group member limit in DEC-39.
- Turning the waitlist off deletes nobody. Existing waitlisted rows still promote. New sign-ups on a full event get refused.

Transition rules under the lock.

- A new `going` request that fits becomes `going`.
- A new `going` request that does not fit becomes `waitlisted` with `waitlisted_at` set to now when the waitlist is on. It gets 409 with `{"error": "This event is full"}` and writes no status change when the waitlist is off.
- `maybe` and `declined` never take a seat and never waitlist.
- `going` to `maybe`, `declined`, or `cancelled` frees seats and promotes.
- `maybe` or `declined` to `going` counts as a new `going` request at that moment.
- `going` to `going` with a larger `guestCount` that no longer fits gets 409. The old registration stays unchanged. Never demote a seated party to the waitlist.
- `waitlisted` to `waitlisted` with a new `guestCount` keeps the first `waitlisted_at`.
- `waitlisted` to `maybe` or `declined` leaves the line and clears the waitlist result for that row.
- Reject a `guestCount` below 0 or above `guests_allowed` with 400. The message names the limit.
- A cancelled occurrence takes no registration writes. Keep the current not-found answer.

### Promotion

Promotion order is `waitlisted_at` and then registration id.
One pass over that order is enough. Each promotion only uses more seats.
A promoted row becomes `going` and gets `promoted_at`. Keep `waitlisted_at` as history.
Skip a disabled or deleted account in the pass. It keeps its place in line.
The 2 hour cutoff is a fixed rule and not a setting. At or after `starts_at` minus 2 hours, auto-promotion stops. Pass `now` into the promotion code as a value. Handlers pass the real clock. Tests pass a fixed clock. Add no global clock seam.
Inside the cutoff, a freed seat writes one cutoff notice to the group leaders or the church-wide hosts. Admins get it only when they also lead or host. The notice links to the event page. It carries no inline button.

### Leader and host actions

Gate every action in this section with `policy.CanManageEvent`. An admin passes that check as today.
Keep the existing route style. Address the occurrence by `date` in the body, as `apiRegister` does.
Write the audit row in the same transaction as the change and its notification.

- `POST /api/v1/events/:id/registrations/remove` with body `userId`, `date`, and optional `note`. It sets `removed`, `removed_by`, and `removal_note`. It writes `registration.removed`. It tells the removed person in the bell and by email. A freed seat promotes.
- `POST /api/v1/events/:id/registrations/promote` with body `userId` and `date`. It promotes that one waitlisted row when it fits, inside the cutoff as well. It refuses with 409 when the party does not fit. It writes `registration.promoted` with the leader or host as actor.
- `POST /api/v1/events/:id/registrations/add` with body `userId`, `date`, `guestCount`, and `overCapacity`. It adds or re-adds a person as `going`. Over capacity works only with `overCapacity` true and writes `registration.added_over_capacity` with the count and the capacity. The SPA confirms first. This action is the DEC-47 path back in for a dropped restore.
- A `removed` row blocks self-registration for that occurrence. The member register route returns 409 and tells the person to ask a leader or host. Only the add action clears a removal. This matches the removed membership rule in DEC-35.
- Self-registration never accepts `overCapacity`. Reject it there with 400 and test it.

### Guests

A guest holds no seat before the emailed link is redeemed. Keep that M1.4 rule.
At redeem, run the locked write path. A guest who fits becomes `going`. A guest on a full event with the waitlist on becomes `waitlisted`. The confirmation email and the manage page state the waitlist position.
A guest on a full event with the waitlist off gets a "This event is full" page. Create no guest user and no registration on that path. Mark the signup confirmed so the link dies.
Guest cancel by manage token leaves `going` or the waitlist under the same lock. A freed seat promotes.

### Promotion email and the "I can't come" link

Reuse the registration manage token. Do not build a second token system.
On promotion, rotate the token and store only its hash in `ManageTokenHash`. The old token dies at that moment.
The promotion email links to the manage page. The page asks for one confirming press and then posts the cancel. A mail scanner that only fetches the page cancels nobody.
Use one manage page and one cancel endpoint for guests and promoted members. Generalize the guest wording. Update the M1.4 tests in the same pull request when a path or label moves.
The token cancel sets `cancelled` for guest and member alike. It frees the seat and promotes under the lock.
The token route stays outside CSRF. Extend the exact exempt list only when the route shape truly changes and update `TestCSRFExemptRoutesAreExact` in the same commit.
Send no SMS on promotion in this milestone.

### Disabled and re-enabled accounts

Disabling keeps registration rows and hides them. It frees every seat that account held on future scheduled occurrences, so run promotion for each one in the disable transaction. Collect notification ids and deliver email after commit, as the disable path does today.
Re-enabling adds a `restoreRegistrations` step beside `restoreMemberships`. Run both inside the existing admin update transaction.
Process only `going` rows on future scheduled occurrences. Order them by occurrence start and then registration id. Lock one occurrence at a time in that order.
A row that fits stays `going` and counts again once the account is enabled.
A row that would overfill is deleted. It writes `registration.not_restored` with the user, the seats used, and the capacity. It sends the person an ask-a-leader notice in the bell and by email.
`waitlisted` rows keep their place and need no restore check. `maybe`, `declined`, `cancelled`, and past rows need no check and no notice.

### Notifications

Add these kinds to `internal/notify/kinds.go`. All use category `events`, allow email, carry no inline action, and never batch. RSVP kinds stay navigation only per section 5.12.

- `event.changed` for a time or place change. The `Vars.Change` field carries the variant.
- `registration.promoted` for "you're in".
- `registration.removed` for pruning. The note reaches only the removed person.
- `registration.not_restored` for a dropped restore.
- `waitlist.cutoff` for leaders and hosts inside the cutoff.

Reuse `event.cancelled` as is.
Change its recipients from `going` and `maybe` to `going` and `waitlisted`. Event changes use the same recipient set.
Set `ExpiresAt` to the occurrence end on every event kind. The read side then files it under Archived.
Use no dedupe key on kinds that can happen twice to one registration, such as promoted and changed. A stable dedupe key would swallow the second real notice.
Send through `notify.Send` inside the write transaction. Pass group names, places, and links only when the recipient may see them. Reuse the current `canSeeGroupIn` guard shape. Never put an email address or a phone number in a kind. The registry test checks that rule.
Guests never read a bell. Their notice is the email copy. Prove the post-commit delivery path sends to status `guest` accounts with a devoutbox test. Stop under the stop conditions when it skips them.
Fan out `event.changed` from both change doors. One door is the per-date occurrence update when time or place changes. The other is a series edit that moves future occurrences or changes the event place. One person gets one item per occurrence per change.

### API and SPA

Update `docs/API.md` and `web/src/types.ts` in the same pull request as the Go JSON. Add each new response pair to `tsContracts`.

- The register response gains the final status, `guestCount`, and `waitlistPosition`. Position is null unless the person is waitlisted.
- The occurrence JSON gains `capacity`, `seatsUsed`, `spotsLeft`, `waitlistEnabled`, and `guestsAllowed`. `spotsLeft` is null when capacity is unlimited and never below 0. The registrations count map gains `waitlisted`. It still counts registration rows, while `seatsUsed` counts seats. Keep those two meanings apart and name them so in the API docs.
- The occurrence JSON gains `myGuestCount` and `myWaitlistPosition` for the signed-in viewer. `myRegistration` may now read `waitlisted` or `removed`.
- Each attendee entry gains `guestCount`. Waitlisted names follow the same `CanSeeAttendeeNames` rule as going names.
- Waitlist position counts waitlisted registrations ahead in promotion order among listed accounts. Compute it on read. Store no position column.
- Event create and edit accept `capacity`, `waitlistEnabled`, and `guestsAllowed`. The per-date occurrence update accepts `capacityOverride`. Use a number to set a value and null to clear it, as the group member limit does.
- The shared `SeriesEditor` carries the new event fields on the group and event pages. State each limit next to its field. Keep valid input on a failed submit.
- The register control shows going, waitlisted with position, full with no waitlist, and removed states. Leaders and hosts see remove, promote, and add controls. The over-capacity add needs a `confirm()` first.
- The attendee list shows going parties with their guest counts and a waitlist section in line order.

### Key decisions

**Decision 1. Remote counting waits for M1.8.**
The milestone scope says 5.4 in full including remote capacity. M1.8 owns the remote flag, remote capacity UI, and its DEC-38 restore rule.
M1.5 keeps one seat bucket and shapes the pure promotion function so M1.8 can add a second bucket without a rewrite.
The rejected option adds `remote_capacity` and `attendance_mode` now with no `remote_available` flag to gate a remote sign-up. That invents a rule the plan gives to M1.8.
Write this split in the pull request body. Get the owner's word against it before the migration lands and stop under the stop conditions.

**Decision 2. Position is computed and never stored.**
Promotion order needs one timestamp and one tie break. A stored position would need rewrites on every leave and promotion.

**Decision 3. Lowering capacity removes nobody.**
This matches DEC-39 for groups and keeps one mental model for leaders.

**Decision 4. A removed person cannot re-register alone.**
Pruning with an open door back in does nothing. The add action is the way back, as with a removed membership.

## Risks and open questions

The highest risk sits in step 2. Every other door reuses that lock, so a wrong count there repeats everywhere. The 50 request test at `-count=5` is the proof that matters most.

One risk sits in the notification recipient switch. Moving cancellation notices from `maybe` to `waitlisted` changes behavior people may already rely on in review builds. The milestone acceptance names going and waitlisted only, so the brief follows it. State the switch in the pull request body.

Remote capacity stays the one open product call. Decision 1 states the default and the stop line. No other open question blocks a claim. The plan says nothing is open in section 15, and this brief adds no new question.
