# M1.9 (and remaining M1.8) judgment calls

Wright, Oct 21, 2026. One entry per call: what I chose and why. Each call is also written into the brief or PR it affects.

1. **Order: finish M1.8 (remote, then childcare) before M1.9.** M1.9 lets household people register and count toward capacity. M1.8 adds `attendance_mode` and `childcare_count` to the same registration row and splits seat counting into in-person and remote. If M1.9 went first, its counting and its "register Mary too" form would need rewriting once remote and childcare land. The two milestones touch the same lock path (`seatsUsed`, `promoteLocked`), so landing the counting model once keeps the M1.9 diff smaller.
2. **Remote seats share the one waitlist.** 5.4 says remote registrations "count against [`remote_capacity`] separately", like Meetup's hybrid events. I keep one waitlist per occurrence, and each waitlisted entry remembers its mode. Promotion fills each pool from the waitlist entries of that mode, in line order. A second waitlist table would add a concept for no gain.
3. **`remote_capacity` null with `remote_available` on means unlimited remote seats.** This mirrors `capacity` (null is unlimited). `remote_available` off means the remote option isn't offered, and the API refuses `attendanceMode: remote`.
4. **Guests follow their party's mode.** A remote party's `guest_count` counts against remote seats. It's the simplest rule and matches Meetup.
5. **Childcare has no waitlist.** When `childcare_capacity` is full, a request for more childcare spots than are left is refused with 409 and "Childcare is full for this date". The person can still register without childcare. 5.4 defines a waitlist only for seats, and a childcare waitlist would need its own promotion rules.
6. **Re-enable (DEC-38/47):** a restore is left out if it would exceed seats in its mode or `childcare_capacity`, with the same "ask a leader" notice and audit row as M1.5.
7. **The M1.8 video boxes get ticked in the remote PR.** Video shipped in #102 with tests (Jitsi, `registered_only`, no iframe). Those boxes were never ticked, so I tick only the verified ones.
8. **M1.9 ships in three slices:** households and links, then registering household people, then conversion and docs. Each slice can be reviewed alone. The first slice touches no registration code, so it can be reviewed while M1.8's counting is still in review.
9. **A household is created lazily** the first time "My household" is used, and named after the holder's last name (editable). That's simpler than asking at signup, and there are no users yet.
10. **Any adult account in a household can manage it.** PLAN says "account holder". I read that as any adult with their own account in the household, with relation guardian or adult. Teens can view their household but not edit it.
11. **A household child counts as a seat when registered by name.** 5.4 and 5.10 say each named person counts toward capacity. Childcare's `childcare_count` stays separate, for drop-in children who aren't named.
12. **Converting a household person goes through an invitation to the new email.** Their registrations move only when the invitation is accepted, so a typo'd email never takes over anyone's sign-ups. It reuses the invitation token path from M1.2.
13. **A converted teen starts `pending_consent`**, using the DEC-69 rule until M1.10 consent records exist.
14. **#106 is backend-only.** Wonder Full drafted the household API client in web/src/api.ts and types.ts but stopped before writing the UI. Nothing used the client yet, so knip (which CI runs) would fail. I dropped those web changes and kept only the `errors.ts` codes. The client comes back with the slice 1 UI PR.
15. **Migration numbers are reserved ahead:** 00020 for remote (#105), 00021 for childcare (not started), 00022 for households (#106). The PRs can land in any order. Goose runs pending versions in order, and none of them depends on another's columns.
16. **`GET /me/household` creates the household on first use**, following the brief. It's a write on a GET, but it is idempotent and only writes the caller's own row. I flagged it for Warden instead of adding a separate POST.
