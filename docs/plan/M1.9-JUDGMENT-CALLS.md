# M1.9 (and remaining M1.8) judgment calls

Wright, Oct 21, 2026. One entry per call: what I chose and why. Each call is also written into the brief or PR it affects.

1. **Order: finish M1.8 (remote, then childcare) before M1.9.** M1.9 lets household people register and count toward capacity. M1.8 adds `attendance_mode` and `childcare_count` to the same registration row and splits seat counting into in-person and remote. If M1.9 went first, its counting and its "register Mary too" form would need rewriting once remote and childcare land. The two milestones touch the same lock path (`seatsUsed`, `promoteLocked`), so landing the counting model once keeps the M1.9 diff smaller.
2. **Remote seats share the one waitlist.** 5.4 says remote registrations "count against [`remote_capacity`] separately", like Meetup's hybrid events. I keep one waitlist per occurrence, and each waitlisted entry remembers its mode. Promotion fills each pool from the waitlist entries of that mode, in line order. A second waitlist table would add a concept for no gain.
3. **`remote_capacity` null with `remote_available` on means unlimited remote seats.** This mirrors `capacity` (null is unlimited). `remote_available` off means the remote option isn't offered, and the API refuses `attendanceMode: remote`.
4. **Guests follow their party's mode.** A remote party's `guest_count` counts against remote seats. It's the simplest rule and matches Meetup.
5. **Childcare has no waitlist.** When `childcare_capacity` is full, a request for more childcare spots than are left is refused with 409 and "Childcare is full for this date". The person can still register without childcare. 5.4 defines a waitlist only for seats, and a childcare waitlist would need its own promotion rules.
6. **Re-enable (DEC-38/47):** a restore is left out if it would exceed seats in its mode or `childcare_capacity`, with the same "ask a leader" notice and audit row as M1.5.
7. **The M1.8 video boxes get ticked in the remote PR.** Video shipped in #102 with tests (Jitsi, `registered_only`, no iframe). Those boxes were never ticked, so I tick only the verified ones.
8. **M1.9 ships in three slices:** households and links, then registering household people, then conversion and docs. Each slice can be reviewed alone. The first slice touches no registration code, so it can be reviewed while M1.8's counting is still in review.
9. **A household is created lazily** the first time "My household" is used, and named after the holder's last name (the API can rename it, but the UI in slice 1 has no Rename yet; slice 2 adds Rename and the address). That's simpler than asking at signup, and there are no users yet.
10. **Any adult account in a household can manage it.** PLAN says "account holder". I read that as any adult with their own account in the household, with relation guardian or adult. Teen accounts have no household view in slice 1: `GET /me/household` returns `{household: null}` for them and Profile hides the card (Warden, PR 106). A read-only teen view can come with M1.10.
11. **A household child counts as a seat when registered by name.** 5.4 and 5.10 say each named person counts toward capacity. Childcare's `childcare_count` stays separate, for drop-in children who aren't named.
12. **Converting a household person goes through an invitation to the new email.** Their registrations move only when the invitation is accepted, so a typo'd email never takes over anyone's sign-ups. It reuses the invitation token path from M1.2.
13. **A converted teen starts `pending_consent`**, using the DEC-69 rule until M1.10 consent records exist.
14. **#106 is backend-only.** Wonder Full drafted the household API client in web/src/api.ts and types.ts but stopped before writing the UI. Nothing used the client yet, so knip (which CI runs) would fail. I dropped those web changes and kept only the `errors.ts` codes. The client comes back with the slice 1 UI PR.
15. **Migration numbers are reserved ahead:** 00020 for remote (#105), 00021 for childcare (not started), 00022 for households (#106). The PRs can land in any order. Goose runs pending versions in order, and none of them depends on another's columns.
16. **`GET /me/household` creates the household on first use**, following the brief. It's a write on a GET, but it is idempotent and only writes the caller's own row. I flagged it for Warden instead of adding a separate POST.
17. **The web type contract for households is left out of #106.** `TestWebTypesMatchGoJSON` checks each JSON shape against an interface in `web/src/types.ts`. With the client dropped, I took the four household entries out of `guards_test.go`. The slice 1 UI PR adds them back together with the types.
18. **`GET /me/household` is read-only now (Warden, approving #106).** It returns `{household: null}` until the household exists, and teen accounts get null too. Creation happens only on `PUT /me/household` and `POST /me/household/people`, through `ensureHousehold`. Judgment call 16 is superseded.

28. **Childcare on promotion (M1.8 slice 3, PR 109).** Overruled by Grier (DEC-80): promotion skips a waiter whose childcare request does not fit the remaining spots when childcare is available and its capacity is set. The waiter keeps the request, age note, and `waitlisted_at`; the next party that fits its attendance pool and childcare promotes. Earlier picks consume childcare in the same pass. Retry promotion when childcare frees, including count reductions, cancellation, decline, removal, disabling, or raising or clearing the childcare limit. Attendance seats must also fit, and the two-hour cutoff still applies. There is no separate childcare waitlist. Migration 00023, not the reserved 00021, because 00022 had already merged.
29. **Children's ages are one free-text field (PR 109 review M3).** I didn't add per-child age inputs. One "Ages" box with the hint "For example: 3 and 7" works for any number of children, keeps one privacy note, and gives leaders enough for drop-in care. Per-child fields can come with household children in M1.9 slice 2, where ages come from birth dates.
30. **Slice 2 batches and responsible holders.** An omitted holder answer is unchanged; omitted people are unchanged; a failed answer rolls back the entire batch. Successful going/waitlisted mixtures are independent answers. `registered_by` is the responsible account, never the last editor. Household people join event attendee lists, not group membership rosters.
31. **Slice 2 adult age evidence.** Refuse an adult household RSVP without a birth date proving age 18 on the church-local day today. Known minors cannot bypass link confirmation by being labelled adult. Saved edits validate the merged date/kind. A child/teen label change keeps a confirmed person link; daily rollover remains later work.
32. **Named childcare is a per-child choice.** A named in-person child may explicitly request one care spot. Remote people consume no care. Do not copy named children into the holder's unnamed count. All care shares DEC-80 capacity and promotion. Turning care off preserves requests with zero effective demand.
33. **Use the specific household privacy row.** Unrelated members get counts without household names, even for adult household people. The event path never grants care access from maybe, waitlisted, removed or cancelled rows. Pending household adults may submit care notes but do not get them back until authorized. Addresses never enter event output or audit values.
34. **Narrow scope for the two existing registration cleanups.** Keep seat-only removal's existing promotion behavior, and defer the separate re-add double-count fix. Household deletion/invalidation, disable, departures, reductions and capacity edits still retry the shared promotion path. These deferrals were explicitly requested for slice 2.
35. **Manager remove and promote take `registrationId`** (PR 110). A household person has no user ID, so `userId` can't name every row. The bodies now use the occurrence-bound registration ID, and attendee rows carry it. This changes the manager API shape; the web client is the only caller.

Four test-side mistakes were fixed (an old childcare SQL match, CSRF on the anonymous manage-link cancel, and the visibility test calling `PUT /events/:id` instead of `/visibility`); no product code changed for them.
37. **PR 110 Illuminator review.** Roster actions stack under the details below `sm` (M1). The household form's childcare-count error is on the field with focus, like PR 109 (M2). Household people show their name, then "Signed up by X"; the household name appears only when it isn't the signer's "<surname> household" (N1). 38. **N5 deferred.** Household answers keep the per-person "Answer for X" select rather than the Going/Maybe/Can't go segmented radios. Swapping them changes every person row's layout and tests. Follow-up for a UI pass, logged in STATUS.md.
39. **Household age bands (Warden, PR 110 N1).** Registration uses PLAN's bands: child under 13, teen 13 to 17, adult 18+. A child or teen aged 18 or older, or a teen under 13, is refused with `household_age_mismatch`. One exception: a `child` aged 13 to 17 can still be registered. PLAN's `accounts.age_rollover` job flags children who turn 13 to their guardians rather than blocking them, and refusing on a birthday would cancel a family's plans without notice. Boundary tests cover 12, 13, 17 and 18 for both kinds.
40. **One clock for household ages (Warden, PR 110 N2).** Eligibility and the displayed age both use the church-local date today (`householdClock`, the church time zone). Rosters used to show the age on the occurrence's date in the event's time zone, so the shown age and the eligibility could disagree around a birthday. The care-notes window still uses the real instant.
41. **Whittler PR 110 fixes.** Holder row locks are `FOR NO KEY UPDATE`. A decline that promotes another holder's waiter inserts a notification, which takes a KEY SHARE on that holder's user row; `FOR UPDATE` deadlocked against it (9 of 60 concurrent declines failed in the new storm test before, 0 after). Migration 00024 keeps the original full unique index on `(occurrence_id, user_id)`; NULL user IDs are distinct, so household rows don't collide, and the index still serves occurrence lookups.
42. **Read counts (Whittler, PR 110).** `GET /events/:id` builds one set of household facts per request and shares it between attendees, the recovery list and "my household" answers; the church time zone is read only when a household person is shown, and the household-video lookup runs only for household accounts. A solo RSVP skips the household account, clock, facts and the in-lock access re-check; named people still re-check under the locks. Measured (master → before → after): solo PUT 8 → 18 → 11; GET /events/:id 14 → 26–29 → 20–22 (solo member, admin, holder). The remaining extra reads are the holder row lock and the household rows' facts. `TestRegistrationReadBudget` holds these numbers.
43. **Calls 31, 33 and 39 confirmed as DEC-81** (Grier, Oct 22, 2026): adult with no birth date refused; teen under 13 or child/teen 18+ refused; a child aged 13 to 17 allowed until the yearly age check exists; leaders see care notes only for a going child; pending household adults write but don't read care notes.
44. **Slice 3 conversion decisions** (Astra's open questions, PR 111).
    1. A converted account inherits no memberships. Its registration rows move as they are, and access to private or invite-only events is judged for the new account from then on, the same as for anyone else.
    2. A teen conversion moves the registrations at acceptance. They keep counting toward capacity, as they did as a household teen, and stay visible to leaders as before. The guardian link stays pending admin confirmation, and the account starts `pending_consent` (DEC-69).
    3. Conversion is refused while the holder is disabled, and for `child` people (no accounts under 13, DEC-8).
    4. Converting an adult needs a birth date proving 18 or older (DEC-81), not a new age checkbox at acceptance.
    5. Sending and resending reuse the existing invitation limits; there is no new mail endpoint without a limit.
    6. The transfer is one transaction: all of the person's rows move, or none do.
    7. Implementation uses the existing 20-per-rolling-day invitation limit for conversion sends and resends, by actor and destination. Audit rows count sends across restarts; suppression returns the normal acknowledgement and leaves an existing token unchanged. Ordinary leader invitations count conversion resends too.
    8. Member guidance is one embedded document, `docs/MEMBERS.md`, served as plain UTF-8 text at `/help/members`. This avoids a Markdown renderer and keeps the single-binary deployment.
45. **Slice 3 review and verification** (Wright, PR 111).
    1. Sol's `tools/verify-household-conversion.sh` and the `cacheDir` option in `web/vite.config.ts` only worked around the Codex sandbox (no Postgres, read-only `node_modules`). Both are dropped. Verification uses the normal Go suite, vitest and Playwright.
    2. The "Accounts and household help" link on the household card is a 44px-tall text action (`min-h-11`), to satisfy the target-size guard in `layout.spec.ts`.
    3. The invite page's "This link can't be used" title is an h2 under the page's h1 (`EmptyState level={2}`). It was a plain paragraph, so screen-reader users couldn't jump to it.
    4. The conversion e2e scenarios need the dev outbox, so CI (production mode) skips them. They were run locally with `E2E_APP_ENV=dev`, and they capture conversion screenshots when `SCREENS_DIR` is set.
