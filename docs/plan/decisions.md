# Fold decisions

### 15.1 Decisions

Every decision here is Grier's. A later decision wins over an earlier one, over the requirement wording and over the repo. Ids are stable: a decision that a later one amends keeps its row with the amendment folded in, and one that a later one replaces keeps a one-line row that points to it.

| DEC-38 | **Admins are labeled on rosters, and disabled accounts keep their memberships** (Grier, Oct 9, 2026). (A) Rosters and any member list a leader sees mark church admins with an "Admin" label, and leaders never get a Remove button for them; the members API exposes an `admin` flag, and the server still refuses (DEC-35). | DEC-39 | **Groups get an optional member limit** (Grier, Oct 9, 2026), because recurring classes meet in rooms with a maximum capacity. Only `active` memberships of non-disabled accounts count, leaders included. A full group refuses self-join ("This group is full"); groups have no waitlist. A leader or admin goes over the limit only by explicit choice (an API override flag; the SPA confirms), and that add is audited; accepting an invitation follows the same rule as the leader's add. Lowering the limit below the count is allowed: existing members stay and joins are blocked until the count drops. Leaders and admins see the count and limit. | DEC-40 | **Roster sync with church management software is a far-future consideration, not on the roadmap** (Grier, Oct 10, 2026; amended by DEC-140: cut, re-entering only as a new milestone when a named church asks; generic CSV import, M4.5, is the answer meanwhile). The goal is that churches can avoid managing rosters in two places. Research: `docs/plan/research/chms-sync.md`. Direction: a new `chms` provider kind following the email/SMS adapter pattern. **One-way only, from the ChMS into Fold; Fold never writes back.** Import with admin review first, then scheduled or webhook-driven updates. Each field has one owner: the ChMS owns names, households and addresses; Fold owns login email, consent, roles, group memberships and registrations. Conflicts go to an admin. **Open design item:** when sync is on, ChMS-owned fields must be locked from local editing in Fold, which means turning off some local management features. Decide carefully, field by field, which features to lock and which to keep, so Fold keeps what matters (consent, minors protections, roles, groups, events, registrations, messaging) before any sync work starts. Match by email first; in a household that shares an email the primary contact becomes the account; name-only matches are suggestions only. Minors: no accounts from import, household members only, guardian links start pending admin approval (DEC-32), consent is never imported, and minors' contact info and sensitive data are not imported. Two pull requests can each add the next migration number and pass CI alone; git merges the second without a conflict, because the file names differ, and goose refuses the duplicated tree at boot. The `Master Protections` ruleset therefore turns on strict required status checks ("Require branches to be up to date before merging"): a pull request merges only when its head contains master's tip and `test`, `web` and `provision` passed on that head, so CI saw the tree that lands. Every writer goes through it: the ruleset requires a pull request, blocks force pushes and has no bypass actors, admins included. A merge queue would save the extra CI run, but GitHub offers it only to organization-owned repositories, and `grierj/fold` is user-owned. A pull request that falls behind master merges master (never rebase) and reruns CI before it can merge; the "Update branch" button (`allow_update_branch`) does that merge. `scripts/merge-rules-check.sh` in CI's test job fails when master's live rules lose strict checks, the pull request rule, the non-fast-forward rule or a required check. Bypass actors are visible only to an admin and stay a review item. Detection and recovery stay as a backstop for GitHub's own merge step: `TestBaselineFileShape` fails a duplicate on every pull request and master push, a duplicated tree never boots, migrates or passes the release smoke (`TestDuplicateVersionNeverBoots`), and the recovery steps are in `docs/agents/migrations.md`. | 14.1, 14.2, DEC-138 |
