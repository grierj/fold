# M1.8 brief: video, remote, childcare

Source of truth: PLAN.md 5.8, 5.3 (event fields), 8.2 (feeds), DEC-16, DEC-38, DEC-47, and the M1.8 acceptance list. M1.8 ships in slices; each is its own PR.

## Slice 1: video links and `video_reveal` (this PR)

- Migration `00019`: on `events`, add `video_provider` (`none|link|jitsi`, default `none`), `video_url` (text, default `''`), `video_reveal` (`always|registered_only`, default `registered_only`), with CHECK constraints. Add the `jitsi_domain` setting read (default `meet.jit.si`).
- Event create and update accept `videoProvider`, `videoUrl`, `videoReveal`. `videoUrl` must be an absolute `https://` URL (max 2048) when the provider is not `none`; `none` clears the URL.
- `POST /api/v1/events/video/jitsi` (leaders, hosts, admins; CSRF) returns `{url}`: `https://<jitsi_domain>/<church-slug>-<12 random chars>` from crypto/rand, no API call. The church slug comes from `church_name` (lowercase, a-z0-9 and hyphens; `fold` if empty). Each call gives a new URL.
- Reveal rule, one policy function `policy.CanSeeVideoLink(reveal, isGoing, isManager)`: `always` shows everyone who can see the event; `registered_only` shows only people registered `going` for that date, plus the event's leaders or hosts and admins. Waitlisted, maybe and declined do not see it (personal feeds widen this for maybe and unanswered members: DEC-70).
- Applied in: the event API (`videoUrl` omitted when hidden; `videoHidden: true` so the UI can say "Register to get the link"), personal ICS feeds (per occurrence, going only, under `registered_only`), and the public feed (only `always`). Emails that carry event details (promotion "you're in") include the link only when the recipient may see it.
- UI: the event form gets a Video section (None / Paste a link / Generate Jitsi link button; reveal select defaulting to "Registered people only"). The event page shows the link as a plain anchor with `target="_blank" rel="noopener noreferrer"`. No iframe or embed anywhere (DEC-16); a test greps web/src for `<iframe`.
- Tests: policy table for `CanSeeVideoLink`; API tests (going sees, waitlisted/outsider don't, leader does, `always` shows all); feed tests (personal and public); Jitsi URL shape and uniqueness; validation of non-https URLs.

## Slice 2: remote attendance (decisions, Oct 21)

- Migration: `events.remote_available` (bool, default false) and `events.remote_capacity` (int, nullable, >= 0); `registrations.attendance_mode` (`in_person|remote`, default `in_person`, CHECK); `event_occurrences.remote_capacity_override` (nullable), mirroring `capacity_override`.
- Counting: in-person seats are `going` in-person parties (1 + guest_count) against `capacity`; remote seats are `going` remote parties against `remote_capacity` (null is unlimited). Disabled accounts never count in either (DEC-38).
- One waitlist per occurrence; each entry keeps its mode; promotion fills each pool from entries of that mode in line order, skipping parties that don't fit (`PickPromotions` per pool). The cutoff rule is unchanged.
- API: `PUT /events/:id/registrations` takes `attendanceMode`; `remote` is refused (400) when `remote_available` is off. Occurrence JSON adds `remoteAvailable`, `remoteCapacity`, `remoteSeatsUsed`, `remoteSpotsLeft`, and each attendee's `attendanceMode`. Switching mode on an existing going registration is a re-register under the lock (may waitlist).
- Re-enable: left out when the restore would exceed its mode's capacity (DEC-47).
- Filter: `GET /api/v1/calendar?remote=1` (and the calendar UI chip "Remote available").
- UI: event form "Remote attendance" (checkbox + optional remote capacity); RSVP shows "In person / Remote" when remote is available; attendee list labels remote people.
- ICS description mentions "Remote attendance available" (8.2).

## Slice 3: childcare (decisions, Oct 21)

- Migration: `events.childcare_available` (bool), `childcare_notes` (text), `childcare_capacity` (nullable), `childcare_ages` (text); `registrations.childcare_count` (int, default 0, >= 0) and `childcare_ages_note` (text, max 200).
- `childcare_count` > 0 only when childcare is available; total going childcare_count must stay within `childcare_capacity` (409 "Childcare is full for this date"; no childcare waitlist).
- DEC-80, Grier, Oct 21, 2026, overrules the slice 3 promote-without-childcare call. Promotion skips a waiter whose childcare request does not fit when childcare is available and its capacity is set. The waiter keeps the request, age note, and `waitlisted_at`; the next party that fits its attendance pool and childcare promotes. Earlier picks consume childcare spots in the same pass. A party needing no childcare can promote when childcare is full. Hand-promoting a specific person returns 409 `childcare_full` if the request does not fit.
- Retry promotion when childcare frees through a going registration lowering its count, cancelling, declining, moving to maybe, removal, or account disabling. Event edits that raise or clear the childcare limit, or turn childcare off, retry future scheduled dates too. Attendance seats must also fit, and the two-hour cutoff still applies.
- Tests: `TestPickPromotionsByPoolChildcare`, `TestChildcarePromotionSkipsUntilRequestFits`, `TestChildcareBatchPromotionsShareRemainingPlaces`, `TestChildcareFreedPromotesOnlyWithSeat`, and `TestManualChildcarePromotionRequiresRoom`.
- Visibility: per-registration childcare counts and notes, and the occurrence's childcare totals, only to admins and the event's leaders or hosts (`policy.CanSeeChildcare`); the registrant sees their own.
- Filter `childcare=1`; ICS description mentions "Childcare available".
- Re-enable: left out when the restore would exceed `childcare_capacity` (DEC-47).
