## T4a departure preview and snapshot contract

T4a adds read-only preview only. It deliberately leaves the existing mutation
routes enabled until T4b can replace their internals without an intermediate
broken flow.

- `GET /api/v1/groups/:id/departure-preview` previews the signed-in account's
  own leave.
- `GET /api/v1/groups/:id/members/:userId/departure-preview` previews an
  authorized group leader or admin removal. Admins use this same route and the
  same implementation; there is no second admin facts path.
- Both run `loadDepartureFacts` in a PostgreSQL repeatable-read, read-only
  transaction, reload the active actor/session, and authorize through
  `policy.CanRetainOccurrenceAfterDeparture`, which in turn uses the existing
  `CanLeaveGroup`/`CanRemoveMember` rules. A hidden group stays 404, a visible
  unmanaged group is 403, and changed membership/leadership returns coded 409
  `departure_unavailable`.
- The response counts only the subject account's scheduled, not-ended Going,
  Maybe and Waitlisted registrations. Declined, cancelled and removed rows are
  already ended answers/lifecycle states and are excluded; past attendance,
  household people and proxy registrations are untouched. Zero rows is a valid
  confirmation context.
- `policy.DecideDepartureDate` is the pure DEC-74 date rule. Underway and
  at/inside-two-hour-cutoff dates are keepable and checked by default. Later
  dates with effective per-date public visibility are keepable unchecked.
  Other future private/invite-only rows count as affected but are not offered.
- Keepable DTOs contain only occurrence ID, original date, effective title,
  UTC start/end, the subject's status, effective visibility, default and reason.
  They contain no attendees, place, group/series ID, recurrence, sibling dates,
  roster or management data.
- `newDepartureSnapshot` emits an opaque AES-GCM token using a domain-separated
  key derived from `SESSION_SECRET`. It binds actor, subject and group to a
  SHA-256 digest of the stable `departureFacts` contract. `parseDepartureSnapshot`
  rejects tampering and cross-actor/subject/group use; `departureSnapshotMatches`
  compares a locked recomputation in constant time. Client counts/date facts are
  never authority.
- The digest covers actor/subject account/session facts, actor and subject
  memberships (including tenure), group state, active leader count, the complete
  affected set, displayed clocks/status/effective visibility and keepability,
  the subject's own registration, and active exact-date access/provenance. It
  deliberately excludes other attendees and capacity/waitlist/guest/remote/
  childcare configuration; current promotion math reloads those resources under
  occurrence locks. This detects newly added/removed subject rows,
  role/membership changes, visibility changes, subject registration changes and
  exact-access changes without staling for an unrelated person's RSVP.
- No observation time is hashed. Recomputing before any boundary stays equal;
  crossing the cutoff/start changes keepability and crossing `ends_at` removes
  the row, so both stale correctly without every passing second doing so.
- DTO fields are paired as `DeparturePreview` and `DepartureKeepableDate` in
  `web/src/types.ts` and `TestWebTypesMatchGoJSON`. The exact contract and the
  exclusion rationale are documented in `docs/API.md`.

T4b lock/TOCTOU handoff:

1. Start the confirm transaction at the global contact gate, but review the
   final order against every competing path before coding. The desired
   departure order is contact gate, group row, current actor/subject account
   rows (stable ID order), membership facts, then every currently affected
   occurrence ID ascending. It must remain compatible with `changeRoleIn`'s
   group-first removal order and account disable/delete's contact/account order.
2. Ordinary RSVP does not universally take `lockContacts`: it first locks the
   responsible account(s), then the occurrence, and retries from a rolled-back
   transaction with contact -> account -> occurrence only when it discovers
   active exact-date access. T4b must not assume the contact gate alone freezes
   an uninvited RSVP. Its snapshot recheck and exact registration reload must be
   under the occurrence lock. Concurrency tests must cover an ordinary RSVP
   added/changed while departure waits.
3. Avoid a group/account/occurrence cycle: do not hold an occurrence and then
   seek the group or account in departure, and do not add a group lock after an
   RSVP account/occurrence lock. The subject account lock is required to stop a
   new own RSVP on a previously unaffected group occurrence while the snapshot
   is being checked. After that lock, compute candidate affected IDs, lock every
   one (not merely client-selected keeps) in ascending order, then reload facts.
   If final implementation needs a different user-row position, inspect
   disable/delete and membership writers for the reverse order and adjust to one

4. Parse the token for the exact actor/subject/group, reload `loadDepartureFacts`
