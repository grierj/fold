# M1.11 — contact privacy and direct-contact requests

## State: implemented, independently reviewed and verified locally

Accepted locally on 2026-10-25 after all five slices, independent corrective
and UI reviews, final integrated gates, and actual sensitive-mail/role-state
proof. All 16 M1.11 acceptance boxes in PLAN.md are satisfied by the matrix and
E1–E7 below. This is implementation acceptance, not publication, merge or
production deployment. STATUS.md is the tracker; PLAN 5.11, section 6, M1.11
and DEC-31/33/75/78 define the scope.

Adults' hide-contact setting defaults off. Teens are always hidden from leaders
and hosts in ordinary presentation. A successful request does not bulk-disclose
fields: the requester must explicitly reveal the granted fields in the granted
context, with an audit committed before disclosure. Self/admin/confirmed-guardian
ordinary contact rights are separate from a leader's rights.

DEC-78 supersedes DEC-75's older exclusion of hidden teens from the picker:
active teens and contact-hidden adults are searchable by name. Every teen add
requires teen and admin approval, including an admin's own request. Reusing
request machinery does not reuse authority: `contact`, `group_add` and
`occurrence_add` have separate policy, DTOs, effects and audit attribution.
An approved group/date ask **never creates a ContactGrant**.

## Safety details beyond the short checklist

### Contact transitions and purpose boundaries

Contact mutation transactions take the shared contact gate first, then current
account/context/request/grant facts under domain locks. Completion/reveal checks
current session, account eligibility, management role, subject relationship,
expiry and requested fields; stale decisions cannot resurrect terminal rows.
Role loss includes demotion, handoff and removal. Host grants end on host removal
or 30 days after the last occurrence. Disable, deletion and teen account-consent
loss end access; restoring role/account/consent does not revive a grant. Actual
church-local adulthood prevents teen-approved access even if DEC-83 temporarily
leaves the stored account type stale. At adulthood the person's own adult
contact preference applies; old teen approval never becomes an adult grant.
The daily advisory-locked sweep is
idempotent; direct mutation hooks enforce immediate endings.

`TestContactAuthorityMutationWinsReveal`, `TestContactDisableWinsPendingTaskDecision`,
`TestContactSweepsBoundariesAndIdempotence` and `TestContactEventGraceAndHostRemoval`
cover these transitions. Rejected hidden-field requests have retained refusal
rows; middleware tests cover unauthenticated/CSRF refusal without falsely
attributing a submitted hidden person ID. Audit failure fails closed.

### Exact-date access is not series access

Explicit invitations bind recipient and stable occurrence with issuer/request
provenance; ordinary registrations and pending asks are not authority. Separate
sanitized GET and own-registration/decline/block endpoints preserve the ordinary
series policy. Hidden group identity/place fallback, hosts, attendees/counts,
series metadata/siblings and management controls are absent. Rescheduling the
same occurrence preserves access; new/generated occurrences never copy it.
Calendar links use `dateUrl`; personal ICS, even `scope=all`, uses standalone
entries, never RRULE/sibling enumeration. Public/group feeds are unchanged.

### History retention, authorization and CSV

History queries retained audit/request/access provenance, not mandatory live user
or context joins. Deleted/nonexistent person IDs can yield retained rows or an
empty 200. Only a currently eligible active adult admin gets administrative
JSON/CSV; private subject/requester views are separate, and guardians get only
authorized active teen grants. No names, contacts, reasons, notes, tokens or raw
metadata are projected. IDs are provenance, never permission to follow a hidden
context. New history IDs/cursors stay decimal strings through signed-bigint max;
this is not an app-wide numeric-ID migration. `TestWebTypesMatchGoJSON` checks
JSON key agreement only; it does **not** establish primitive TypeScript types.
Exact-string behavior has dedicated HTTP and client/component tests.

CSV exports all matching rows, not the loaded page, using explicit safe filters,
fixed columns, proper quoting/CRLF and formula protection (significant leading
`= + - @`, controls/format characters). A REPEATABLE READ snapshot is materialized
in a 0600 temporary file with page-bounded Go memory. Flush/Sync/Seek/Stat and a
final locked current-actor eligibility/session check precede export audit/commit
and protected bytes. Concurrent demotion/session change/disable/deletion fails
closed; post-commit revocation cannot retract an already authorized prepared
export. `contact_history.exported` records preparation, not confirmed receipt.

## Accepted limitations and deferred scope

- Ordinary event childcare editing remains available through ordinary authority.
  Scoped EventDate preserves existing care options by omission and has no care
  editor. Its DTO has no seat-count/waitlist-position fields; UI does not invent
  them. E3 retains manager-only care-preservation JSON separately from recipients.
- CSV server memory is page-bounded, not aggregate temporary disk, concurrent
  exports, database work or transaction duration. Browser fetch buffers a Blob
  proportional to export size. Process crashes can leave temporary files; normal
  success/audit/query/authority error cleanup is tested, not every filesystem fault.
- Downloaded contact values/ICS/CSV cannot be recalled from another application.
  Existing unrelated numeric-ID APIs can lose precision before history navigation;
  exact manual retained-ID entry is not a general bigint conversion.
- Full M1.14 ghosting/month dots, series responses/Undo, join/leave previews and
  registration changes, global own-scope/discovery/window rules and generalized
  block management remain deferred. M1.13 per-date visibility also remains out.
  Messaging relay, SMS sending, recipient composition and general guardian copies
  are future work. DEC-33 tamper-evident/hash-chain audit hardening is not built.
- E6 proves existing unconditional transactional safeguarding copies to confirmed
  guardians, not the future optional general-message `guardian_copies` preference.
  It verifies plain-text mail and the HTML outbox viewer; the mail model has no
  HTML MIME part. Eight emitted kinds are covered, not every un-emitted kind.
- E7 is the final integrated source verification. Subsequent acceptance edits are
  documentation-only; raw private proof is not committed or published. External
  SMTP inbox delivery, production deployment and later CI/PR checks are separate
  from this local milestone verification.
