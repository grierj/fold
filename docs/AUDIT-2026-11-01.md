# Fold audit — 1 Nov 2026

Full-project audit against the stated goals in `docs/plan/PLAN.md` and `AGENTS.md`.
Historical decisions (DECs) were treated as reversible where reversing them makes a
better product, as long as goal-meeting functionality stays.

Method: 8 independent read-only audit angles (goals fidelity, backend architecture,
security, data/DB/performance, frontend/UX, tests/ops/deploy, product strategy,
code health), then a critic pass that re-opened source for the riskiest claims,
then synthesis. Nothing was executed: no binary, tests, browser, live database,
or `docker compose up` was run. Runtime and scale claims below rest on source
reading and are marked as such. HEAD audited: `3ec934e`.

## Verdict

Fold's group/event/RSVP/safeguarding engine is deeper and more disciplined than
its stated ChurchTrac-slice goal requires — pure policy functions,
lock-then-recheck concurrency, stored notifications and guard tests are
unusually strong for the product class. But no church runs it yet, and the
volunteer-operator layer that would let one do so (prebuilt images, backups,
setup wizard, CSV import, email provisioning, TOTP) plus the headline SMS
promise are unbuilt, while push and rooms depth were built ahead of that v0.5
spine. Code health is good enough to keep building on — the risk is sequencing
and surface breadth (38 models, DEC-136, meta-test apparatus), not correctness
of the core. Fix the setup race, ship the activation spine, and freeze new
surface until a first church is live.

## Security summary

Posture is unusually strong: fail-closed centralised policy, hashed single-use
tokens, atomic Postgres throttles, exemplary push SSRF defences, and guard tests
(CSRF-exact list, `groupShownTo`, log redaction). No code-level auth bypass,
SQL injection, stored XSS, or SSRF was found in the surfaces opened. One
realistically exploitable issue survived independent verification:

- **SEC1 [SECURITY-CRITICAL] First-run setup takeover / double-admin race.**
  Anonymous internet user POSTs `/setup` on a fresh public deployment before
  the volunteer finishes (Caddy publishes immediately), or two concurrent
  POSTs both pass the check and create two `RoleAdmin` users.
  Evidence: `main.go:521` (`setupRequired`), `main.go:559` (`handleSetup`
  check-then-Create, no transaction/lock/token), `main.go:576` (`RoleAdmin`),
  `docker-compose.yml:60`. Verified again by the parent agent against the
  current tree (no `SETUP_TOKEN` exists anywhere).
  Fix sketch: one-time setup token printed to logs or `SETUP_TOKEN` env,
  plus a transaction with `pg_advisory_xact_lock` and re-count inside the
  lock (pattern in `push_keys.go:117`). Effort M.
  Filed as [#240](https://github.com/grierj/fold/issues/240) (label `security`)
  and fixed the same night in `28268b3`; the issue is closed. No church runs
  Fold yet, so no live data was exposed.

Everything else security-flavoured was demoted to hardening and bundled into
R5 and R12: people-search membership disclosure, EXIF GPS retained in uploads,
logout not invalidating a copied cookie, permanent bearer email/feed links,
private titles on room door-display feeds, missing HTTP timeouts, dangerous
config values accepted silently. Handler-level authorisation coverage was
sampled (~12 areas), not exhaustive over all routes — see "Not verified".

## How to use this document

Each recommendation has an ID. Reply with the IDs you approve, reject, or want
changed (for example "approve R1–R6, R9 with X, reject R8"). Approved items get
a detailed implementation plan suitable for handing to coding agents, in
`docs/plan/` style: slices, files, migrations, tests, acceptance checks.

Effort key: S ≤ 1 day, M ≤ 1 week, L > 1 week.

## P0 — before a first church goes live

### R1 [BUILD] Ship the v0.5 activation spine
GHCR prebuilt image as the only documented path + backup in root compose +
setup wizard/`fold doctor` mail gate + CI compose smoke. Biggest missing
first-church capability: today `docker compose up` compiles Node+Go on a 1 GB
droplet (can OOM), backups cover only DigitalOcean-provisioned installs, and
email can silently be `NoSender`, so a "successful" deploy cannot invite
anyone. Evidence: `docker-compose.yml:20`, `deploy/digitalocean/provision.sh:291`,
`main.go:187`, `README.md:44`, `docs/plan/PLAN.md:1533`, `docs/plan/PLAN.md:2022`,
`.github/workflows/test.yml:15` (CI never boots the shipped compose stack).
Effort L. Risk: release-engineering delays features; slice image/backup/wizard.
Reverses: none (implements M5.1/M5.2/M4.2/M4.4 as planned).

### R2 [BUILD] Generic people CSV import
Name, email, phone, groups — unblocked from the ChurchTrac-sample gate. A first
church's 200 members can today only be added one-by-one by invite/admin-create.
Every church has a spreadsheet; none has produced a ChurchTrac export.
Evidence: `api.go:661`, `api.go:800`, `docs/plan/PLAN.md:1971`,
`docs/plan/PLAN.md:1226`. Effort M. Risk: duplicate/merge semantics need care;
reuse existing invite/verification mail. Reverses: DEC-15's import gate.

### R3 [BUILD] Admin TOTP + people/own-data export
Fold is internet-facing software holding minors' data; TOTP is already called
required-from-v0.5, and with only contact-history CSV leaving the system a
church is locked in. Evidence: `docs/plan/PLAN.md:2010`,
`docs/plan/PLAN.md:1032`, `docs/plan/PLAN.md:1053`, `api.go:589`.
Effort M. Risk: low; token/session machinery exists. Reverses: none (M4.9).

### R4 [CHANGE] Make account deletion actually erase personal data
`apiAdminDeleteUser` rewrites email and soft-deletes but leaves name, display
name, phone, avatar key/blob, birth date and password hash, contradicting
PLAN's erasure promise. Inventory all 38 models + blobs + audit rows and state
retained-vs-anonymised-vs-deleted for each before fixing. Evidence:
`api_admin.go:842`, `api_admin.go:879`, `models/models.go:137`,
`docs/plan/PLAN.md:1054`. Effort M. Risk: must reconcile retained audit rows
and household/consent records deliberately. Reverses: none (PLAN 10.1).

### R5 [CHANGE] Privacy/session hardening bundle
People-search group names only where `CanSeeRoster`/shared; bump
`SessionVersion` on logout + rotate CSRF at login; strip EXIF by re-encoding
uploads; "Reserved" for every non-public room-feed date; refuse `/0`
trusted-proxy ranges, non-https `SITE_URL`, insecure cookie in prod; uniform
invite-friend answer; HTTP server timeouts. Each is a concrete leak past an
existing rule (roster privacy, copied-cookie replay for 7 days, GPS in
avatars, private titles on door displays). Evidence: `api_people.go:253`,
`internal/policy/policy.go:76`, `api_auth.go:294`, `api.go:365`,
`api_profile.go:428`, `api_room_feeds.go:294`, `config.go:107`, `main.go:147`.
Effort M. Risk: low; local changes with existing tests to extend.

### R6 [CHANGE] Notification delivery becomes a transactional outbox
Retries, dead-job admin alerts, password-reset via jobs. 51 hand-remembered
post-commit delivery calls can silently drop email+push; the promised "later
delivery pass" does not exist; dead jobs alert nobody; a crash after the
reset-token transaction loses the email forever. Evidence: `api_groups.go:154`,
`api_notifications.go:821`, `api_notifications.go:859`,
`api_notifications.go:981`, `jobs_daily.go:34`, `internal/jobs/jobs.go:286`,
`api_auth.go:478`. Effort M. Risk: medium; touches every notify caller, but
the queued delivery table already exists.

## P1 — sequencing fixes and the pre-live window

### R7 [CUT] Freeze web push; strike SMS from headline promises until funded
Push took 8 slices / ~9k lines and 20 of the unrun first-church hand-checks for
a 6-step iOS dance most members will abandon, while the SMS headline promise
is currently false. Email + bell + already-shipped push is a defensible v1.
SMS, when a church will pay, should be Telnyx broadcast-only + STOP/START.
Keep shipped push behind the existing church switch; spend nothing more on it.
Evidence: `docs/plan/PLAN.md:42`, `docs/plan/PLAN.md:2226`, `AGENTS.md:259`,
`STATUS.md:39`, `docs/FIRST-CHURCH-CHECKS.md:7`,
`web/src/pages/NotificationsSetup.tsx:34`. Effort S. Reverses: DEC-121
sequencing; amend DEC-43/DEC-125 so "self-contained" means nothing extra to
operate, not reimplementing protocols.

### R8 [CHANGE] Add `self_signup=open`
Verified-email auto-active (teens still `pending_consent`), beside
`off|request`. A volunteer admin who checks weekly is the #1 activation
bottleneck, and approval gates now stack four deep against the plan's own
"trust the church body" rule. Joining style should be the church's choice.
Evidence: `docs/plan/PLAN.md:263`, `docs/plan/PLAN.md:2109`,
`docs/plan/PLAN.md:2139`, `docs/plan/PLAN.md:1202`. Effort M. Risk:
low–medium; decision path and verification mail exist. Reverses: DEC-4's
"no open signup mode".

### R9 [CHANGE] Squash migrations into one baseline (highest-leverage simplification)
Before the first church, squash the 61 migrations into one clean baseline with
real `date`/`timestamptz` types, and fold `OccurrenceAccess`/`ManagerAddBlock`
provenance into `registrations`. Mutable history makes this cheap now and
impossible after go-live. It deletes dual-write triggers, a per-recipient
fallback, text-date invariants, and a 14-day expand/contract process priced
for multi-replica deploys this single binary does not have. Evidence:
`migrations/00001_baseline.sql:2`, `migrations/00005_events.sql:15`,
`models/models.go:437`, `models/models.go:997`, `reminders.go:294`,
`AGENTS.md:180`. Effort L. Risk: medium; guarded by the drift test and
down/up migration tests. New decision needed: replace expand/contract with
additive-first + next-release contract.

### R10 [BUILD] Pull the leader attendance roll forward from Phase 6
PLAN tags simple attendance Core because it is the number pastors ask for
weekly, yet there is no attendance model at all. For a ChurchTrac switcher
this outranks room suggestions and sign-up sheets, and reuses the occurrence
roster. Evidence: `docs/plan/PLAN.md:1461`, `docs/plan/PLAN.md:2079`,
`models/models.go:297`. Effort M. Risk: low. Re-sequences M6.3.

### R11 [CHANGE] Fix the three query-shape ceilings plus pool cap
Incremental `Extend` from `max(original_date)`; batched `reminderReaders`
(today ~2000 queries for one 500-person reminder); `idx_jobs_running_lease`
for push-burst claims; SQL-side visibility/LIMIT for common cases; explicit DB
pool cap (20/5). Postgres is not the ceiling; these five spots are. Estimates
are from query shapes — no EXPLAIN was run. Evidence:
`internal/events/extend.go:35`, `reminders.go:274`,
`migrations/00051_jobs.sql:24`, `internal/jobs/jobs.go:220`,
`api_events.go:102`, `db.go:22`. Effort M. Risk: low–medium.

### R12 [CHANGE] SESSION_SECRET rotation runbook + versioned link expiry
One secret keys sessions, VAPID (loss wipes every push device) and every
unsubscribe link ever emailed, so a post-compromise rotation permanently kills
the unsubscribe path in old mail. Bearer email-settings tokens also never
expire and ignore category scope. Dual-key verification via the existing
version byte; document the full rotation sequence. Evidence: `main.go:81`,
`push_keys.go:145`, `email_unsubscribe.go:19`, `email_unsubscribe.go:29`,
`api_email_settings.go:151`, `cli.go:155`. Effort M. Risk: low.

### R13 [KEEP] The big bets stand
Single-tenant many-deployments (no `tenant_id`, no billing, hard isolation for
teen/consent data), Postgres-only, single Go binary + embedded SPA,
pure-function policy package, stored notifications, guest-link RSVP, and
safeguarding depth as the differentiator. Reversing any of these now is
effort L for zero first-church value. Set a written fleet-tooling trigger at
~5 hosted churches instead of multi-tenancy. Evidence:
`docs/plan/PLAN.md:44`, `docs/plan/PLAN.md:1256`, `docs/plan/PLAN.md:2106`,
`internal/policy/policy.go:1`, `main.go:295`. Effort S (write it down).
Explicitly do not reverse DEC-1/DEC-24 or the single-tenant model.

## Not verified (named gaps)

- Nothing was executed. All performance ceilings are arithmetic from query
  shapes: no EXPLAIN, no seeded large database, no `make test`/`make e2e`, no
  live compose boot, no browser. Scale numbers are estimates.
- DST transition instants are untested and unspecified (`ParseWall` does no
  existence/ambiguity check): a 02:30 spring-forward or 01:30 fall-back event
  needs a decided reject-vs-normalise rule. `internal/events/expand.go:65`,
  `internal/events/expand_test.go:22`.
- Handler authorisation was sampled, not exhaustive: admin, profile, contact,
  room-series and registration internals past sampled windows, plus an
  endpoint-by-endpoint `docs/API.md` diff, remain open.
- Uploads restore is unproven: backups tar `/data`, but no restore that
  re-extracts it and boots against it was run; `--restore-test` counts tables.
- Token pages newcomers open from email (`/invite`, `/set-password`,
  `/guest/*`, guardian consent) are absent from the a11y/layout page list;
  390px/a11y claims there are unverified. `web/e2e/ui-pages.ts:36`.
- Church time-zone change semantics (`apiSetTimezone`: no audit row, no
  re-expansion, feeds in current zone) need a stated intended rule.
  `api_events.go:47`, `api_room_feeds.go:197`.
- Setup page offers only 9 time zones in its datalist; every other church must
  type an exact IANA name. `templates/setup.html:43`.
- Open PLAN decisions DEC-76, DEC-78, DEC-40 could not be judged built vs
  missing. Vendor pricing/10DLC facts were not re-verified live.
- Dependency CVEs (`govulncheck`), TLS posture beyond the Caddyfile, and email
  rendering end-to-end were not assessed.

## What the audit says not to do

- No multi-tenancy rewrite, no framework/language churn, no big-bang package
  split (R13, R18). The core architecture is not the problem.
- No new product surface until a first church is live, except the P0 on-ramp
  items. Breadth is the current failure mode, not depth.
- Do not cut shipped safeguarding, policy purity, or guard tests that cover
  security/privacy/contracts. Tier the rest (R18).
